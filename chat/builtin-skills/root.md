# Root

Coordinate the authorized objective, acceptance, scope and user constraints. Report only evidenced outcomes; proposal acceptance, provisioning, start and completion are distinct.

When available, use `ragent_organization_read` with `action: "skills.list"`, then `action: "skills.read", args: {id, expectedHash: contentHash}` using the current list entry. For authorized root Runs, `candidates.query` takes `args` including `agentId`, optional `taskRole` (manager, specialist or reviewer), `nodeKey`, `tool`, `provider`, `model`, `requirements`, `offset` and `limit`; supply the collaboration task role when known; otherwise the Agent profile role is used. This query does not authorize execution. Follow pagination and treat unknown availability, quality and cost as unknown. `state.get` reads the scoped projection.

For a bounded organization proposal, use `ragent_organization_action` with `action: "plan.submit", args: {proposal}` when available and authorized; use `ragent_organization_read` with `action: "plan.status"` to inspect an uncertain submission. If the tool is unavailable, use the proposal marker specified in the leadership instructions. Do not submit the same operation through both paths. Authority and actual outcomes come from server responses. After a successful frozen proposal, or in a later authorized root Run, use `ragent_organization_read` with `action: "phase.list"` to inspect current phase IDs, dependencies and readiness. `ready_for_admission` only means dependencies and session bindings appear ready; dispatch still checks live policy, budget and runtime. Use the returned phase IDs to call `ragent_organization_action` with `action: "phase.dispatch", args: {phaseId}` for each ready phase. Dispatch acceptance means work was started or accepted, not completed. End the planning turn after dispatch so managed work can run asynchronously; the runtime will bring results back for synthesis. Do not wait in a polling loop or repeat delegated work. The server binds dispatch to this authorized root Run and the organization’s current frozen revision, enforces dependency gates and uses a stable dispatch identity.

For an aggregation Run, use `ragent_organization_read` with `action: "result.read", args: {collaborationId, packetId, offset}` to read an authorized result in pages; follow the returned pagination until complete. Use the session-control skill for authorized CLI and API routes. Scoped team messages support `ragent team-message ack <messageId>` and `reply <messageId> --text <text> --idempotency-key <key>`. A scoped work Run may report `ragent blocker-proposal --kind <dependency|permission|budget|requirement|other> --reason <text> [--suggestion <text>] --idempotency-key <key>`; a scoped reviewer uses `ragent review-opinion` with candidate work item, digest, contract revision, execution epoch, verdict, reason and idempotency key. Result reporting follows the Run's own contract, not an assumed write capability.

For an interrupted collaboration, first inspect its attempt and reconcile effects; `recoveryReceipt {source, consumed}` is a clue, not proof of no side effects. `incident.get` reconciles a bound Run and cannot cover failures before a Run exists. Authorized `POST /api/collaborations/:id/retry` is limited to a valid one-use pre-dispatch receipt and current frozen policy, budget and binding checks. Do not blindly retry unknown outcomes. Incident acknowledgement or resolution is not proof of recovery.

## Organization proposal contract

A proposal uses `schemaVersion: 1`, a stable `idempotencyKey` (or `proposalId`), `objective`, non-empty `nodes`, `phases`, and top-level `acceptance`. Each node needs `stableKey`, `role`, `agentId`, and `phaseId`; roles are `manager`, `phase_lead`, `specialist`, `worker`, `writer`, or `reviewer`. Optional node fields include `parentKey`, `capabilities`, `scope`, `runtime`, `runtimeRequirements`, `runtimeRationale`, and `acceptance`. `runtime` may specify `tool`, `provider`, `model`, and `effort`; select from actual catalog facts and user locks. For read-only work use an empty `scope.writablePaths` and only granted capabilities.

Every node in an accepted initial proposal is intended for actual provisioning, not a placeholder. Honor the user's requested order for initial and later creation: do not include a node initially when the user assigns its later creation to an authorized manager. If the current proposal contract cannot represent that order while preserving required independent review, report the constraint rather than weakening review or claiming that a later node already exists.

Each phase needs `phaseId`, `objective`, and a non-empty `acceptance` array. Top-level, phase, and optional node acceptance entries are objects with non-empty `criterion` (or `id`/`name`), optionally `description` and `evidenceRequired`; they are not bare strings. A phase defaults to requiring review and then needs non-empty `reviewerRoles`; explicitly `reviewRequired: false` disables that phase requirement. The proposal `reviewPolicy` defaults to requiring at least one reviewer node; when review is explicitly not required, set `required: false` and `minReviewers: 0`. Do not weaken review when the actual task or authorization requires it. `manages` entries contain `parentKey` and `childKey`; dependencies and parent relationships must reference known keys and be acyclic.

`runtime.tool` selects the execution harness. `runtimeRequirements.tools` names task-required tools supported by verifiable candidate evidence; it is not the harness identifier. `runtimeRequirements.environment` names a verifiable execution environment, not an access mode. Specify access as `scope.accessMode: "read_only"` or `"writer"`; unknown tool or environment evidence cannot satisfy a hard requirement. Omit requirements that the task does not require.
