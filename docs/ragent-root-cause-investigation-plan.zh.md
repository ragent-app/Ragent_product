# 提醒交付相关故障：根因调查方案

## 范围与基线

本方案仅规划调查，不执行测试、部署、服务操作或 owner 操作。调查对象依次为原始 `Native codex provider preparation failed`、旧会话 hook 拒绝、owner `OSV_INSPECTION_TIMEOUT`。MCP readiness 超时是独立旁支；只有同一原始 Run 的证据建立关联后才纳入第一项因果链。固定文字直接交付、跨 Run 子代理绑定及其他新功能不在本方案内。

现场已安装 0.0.93，其构建源码为 `55cdb7d0a58bdde9faa16109ad3f7cf1ce96ffb8`；此前验收文档提交 `6827e30f` 已包含在编写时 main 的 `eddfb0b12f90ec85597dadcf4e91a783eab1e137` 中。此为已有记录，不代替调查执行时重新确认的安装文件身份。工作继续使用当前工作树和 main；开发、QA 的可配置产物默认放在 G:/AgentoC，保护其他人的未提交修改和活动产物。证据入口为原始方案 `G:/AgentoC/ragent-trigger-delivery-remediation-plan-20261113.md` 第 9、10 节和本仓库 `docs/trigger-delivery-windows-acceptance.zh.md`，尤其第 49、77、79、81–89 行；行号随文档演进可能变化。

## 统一决策门

1. **A：只读盘点一次。** 在有权访问范围内按已知时间、原始 session/request/trigger/Run 关联定位现有记录，保留版本、UTC、阶段、稳定码、结果及各方身份的最小投影。若已有证据足以区分假设并解释完整因果链，不做复现。
2. **B：确定历史证据缺口。** 原始 Run 或关键记录无法取得时，明确记录“历史事件不可追溯”，以及具体缺失项；不得以新运行成功或相似报错回填原案。后续目标仅为当前同类故障。
3. **C：判断观察能力。** 现有正式诊断能提供区分字段时，才计划一次与问题直接相关的真实操作；不能区分时先提出仅含固定阶段、布尔值和稳定码的最小观测补丁，评审后再决定是否部署。需新测试或测试基础设施时，先取得用户明确授权；既有真实验证也须满足本阶段身份、数据和运行条件，不盲测。
4. **D：因果与修复。** 捕获具体失败阶段、触发条件和下游影响，并排除竞争解释后才提出最小修复；在相同条件下使用可信既有检查或必要真实操作验证，保留失败前后关联。不能捕获关键环节时，只报告现象和剩余假设。

每项先做一次有界证据盘点；需要复现时，每轮至多一次指定操作，观察自然结束及既定诊断，不并发重复。达到区分条件即停；身份/关联不明、权限拒绝、安全门禁拒绝、出现无关活跃任务、证据不足或容量不足时停止，记录具体原因。不得修改 ACL、跳过身份校验、读取无关用户内容或凭据、擅自重放已有提醒；也不以反复重启或 MSI 更新代替诊断。必要维护需先确认权威 Run 状态并走正式 drain/恢复流程。

## 一、原始 provider 准备失败

**事实与未知。** 原始外层文本说明准备失败，但尚无能证明具体底层原因的原 Run 关联证据。历史 `providerPreparation.causeCode`、阶段、attempt、准备发生在 runner 提交之前还是之后，以及原始 provider/认证状态均待核。后续成功执行或其他 Run 的 MCP 超时不证明原案原因。

| 可区分假设 | 最小证据及排除条件 | 仍需保留的不确定性 |
|---|---|---|
| 账号或凭据准备失败 | 同 Run 的准备阶段、稳定 code/cause 和认证结果；同一阶段明确完成且失败发生在后续阶段可排除 | 不输出凭据；缺原始事件不能归因账号 |
| 本地 provider home、配置或访问失败 | 同 Run 解析/准备阶段及受限错误类别；已完成对应阶段且有后续首个失败证据可排除 | 不读取无关 profile 或以拒绝访问为借口绕过 ACL |
| supervisor/runner 尚未接收，或提交后状态未知 | 同 request 在对应路径有记录时的 launchStage、提交/受理时间和 Run 状态；权威受理证据可排除“未提交” | 受理不等于执行或发布；launchDefinitelyNotSubmitted 是内部错误标记，不保证持久或 API 可读，缺失不能倒推未提交 |
| 外部 provider 或后续 MCP 环节失败 | 同 Run 实际阶段、原始 provider/MCP 稳定码和时间；准备在该环节前失败可排除为首因 | MCP 超时若来自其他 Run，只能作为旁支 |

**操作与验收。** 一次只读盘点后，缺原 Run 即停止历史归因；若当前同类问题需复现，只用独立授权会话及现有真实 provider，采集同一 Run 的 `providerPreparation` 阶段/cause、launch 提交边界和原始稳定错误，不记录密钥或请求正文。只有“触发条件 → 首个失败阶段 → 有界原因 → 对该 Run 的影响”均由关联记录支持、竞争假设可排除，才称找到根因。

## 二、旧会话 hook 拒绝

**事实与未知。** 曾观察到 `HOOK_RESPONSE_INVALID` 和 `HOOK_CLAIM_UNMATCHED`；后续旧会话的模型文字复述历史错误而无新 commandExecution，不能当成新的拒绝。0.0.92/0.0.93 新鲜会话实际读取成功，不证明旧拒绝原因已修。诊断字段只作观察，不能授权请求。

| 可区分假设 | 最小证据及排除条件 | 仍需保留的不确定性 |
|---|---|---|
| 原始请求与 hook claim 在身份、thread、turn 或时效上不匹配 | 同 Run 的原始 hook 事件、可用的固定 reason/basis/flags、UTC 及服务侧对应阶段；完整匹配且另有明确失败阶段可排除 | basis/flags 从 0.0.92 起仅在部分可关联候选上可用；thread-only、ambiguous 或缺事件均不足以选定原因 |
| broker/owner 的连接或生命周期失配 | 同 Run、同账户绑定的既有生命周期稳定码和对应阶段；有同次已匹配处理与直接响应证据可排除 | 单凭旧进程存在、handoff 成功或管理员管道拒绝不能推断归属 |
| 响应前无 ID 通知影响解析 | 同一次受限消息顺序和最终解析码；有完整顺序观测、无该通知且有其他直接拒绝证据才可排除 | 原始 socket 帧及通知顺序不保证持久化；不足时须先设计受限顺序观测，后续成功不能证明历史命中该竞态 |
| 模型复述历史而非当前工具失败 | 当前 Run 的原始 commandExecution/hook 请求与结果；存在同次真实拒绝才可否定仅复述 | 无原始事件时不能判定当前执行路径 |

**操作与验收。** 先只读比对原 Run 原始工具调用/结果和现有固定字段，不以助手答复代替工具证据。若仍缺关键字段，先提交有界观测设计，不扩大授权；必要时只在新建专用会话做一次真实只读文件操作，按同一 Run 采集服务诊断及实际工具结果。只有原始请求、匹配或拒绝阶段、稳定原因与实际操作结果贯通，才能对该次拒绝定因；旧案缺证则保持未定。

## 三、owner 60 秒检查超时

**事实与未知。** 曾记录 `OSV_INSPECTION_TIMEOUT`，随后在全 Run 终态和正式 drain 下仅重启 ControlPlane，正常 owner CLI 与 health 恢复 ready；这不说明检查卡在哪一步或根因已消除。历史 `OSV_RECOVERY_REFUSED` 也不能自动归于此次超时。

| 可区分假设 | 最小证据及排除条件 | 仍需保留的不确定性 |
|---|---|---|
| 受控检查某子阶段耗时过长 | 自然复现时各固定子阶段开始/结束及耗时、最终状态码；各阶段都在期限内且有其他明确失败可排除 | 目前子阶段耗时未持久投影；拟新增受限观测，最后未结束阶段只定位等待位置，不能直接断言原因 |
| 子进程启动、退出或 IPC/资源等待异常 | 对应阶段固定启动/退出/等待结果及受限进程归属；完整正常结束并交付结果可排除 | 启动/退出耗时目前未持久投影；需区分启动失败、拒绝、资源等待与外部阻塞，不能按进程名猜归属或读取完整命令/密钥 |
| 信任、身份或权限检查被拒 | 同次固定拒绝码和所属阶段；检查成功且后续阶段首失败可排除 | 不为验证改变 ACL、身份或安全门禁 |
| 健康检查与 activation 生命周期时序异常 | 同次 activation state/code 及关联检查事件时间；时序完整且首个失败位于检查内部可排除 | 单次 `inspecting` 为瞬态，不能作为 ready 或故障结论 |

**操作与验收。** 优先分析已保存 10:51 UTC 超时前后的受限日志。若只有总超时而无区分字段，提出阶段观测补丁并评审，不延长全局超时。自然再现或经阶段准入的一次正常 owner 操作中，只记录固定阶段、耗时、状态和错误类别；出现权限拒绝即停止。需证明具体检查阶段为何超时及其与 activation 失败的直接关系，才能称找到该次根因。
