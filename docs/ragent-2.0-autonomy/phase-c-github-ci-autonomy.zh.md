# 阶段 C GitHub CI 自治闭环

[上一阶段 B](phase-b-responsibility-events.zh.md) · [返回总览](README.md) · [下一阶段 D](phase-d-context-organization.zh.md)

目标：将已有 CI 观察脚本迁移到持续责任与 Factory 执行链，使一次责任授权能够产生后续受限工作。本阶段完成后，与 A、B 一起构成 Ragent 2.0 MVP。

前置条件：A 的执行和验收路径、B 的责任/政策/事件/wake 已满足退出条件。选择已有真实项目和来源明确的检查；没有真实证据时不宣布自治闭环通过。

## 工作包和顺序

| 工作包 | 实施内容 | 交付 |
| --- | --- | --- |
| C1 观察入口迁移 | 复用已有失败筛选、日志采集和快照；转换持久事件 | 受限 Observer 与旧入口切换方案 |
| C2 确定性决策 | 核对新事实、已有工作、冷却、权限、预算和事件有效性 | Observe / Decide 及决定回执 |
| C3 工作流准入 | 固定模板、有限服务主体、节点选择、合同与版本检查 | 受限 Factory command adapter |
| C4 验收审批与汇报 | 候选、真实检查、独立意见、人工 Gate 和 Activity | 从事件到结果的完整关联 |
| C5 有界灰度 | 单项目/组织/实例先行，验证恢复并消除双入口 | MVP 证据、风险和回滚记录 |

## Supervisor 的职责收缩

Observe 读取事件、当前责任、关联 Work Graph、组织授权、预算和真实运行事实；无新信息不调用模型。Decide 首版使用 CI 维护固定政策和工作流模板，确有必要时才让模型提出诊断或重新规划建议。Dispatch 指提交经过验证的 Factory 命令，Run 派发仍归现有 Scheduler。

新服务主体必须有独立、有限的 capability；不能复用 owner，也不能仅因名称为 supervisor 自动获得所有 `factory.*`。首次授权约束模板版本、仓库、目标分支、可写路径、检查命令及发布权限。外部日志和记忆只能提供事实，不能扩展这些约束。

责任输入摘要不变、已有关联任务未结束、冷却未到、预算不足、授权过期时，确定性代码作出等待决定。每次唤醒有事件、决定、工作流、Work Item、Run、候选和回执链；成功不依赖 Agent 的一句“已完成”。

## GitHub CI MVP 的实际边界

复用已有脚本按 branch/workflow 选择最新失败、settle window、日志采集及快照。改造的首要目标是停止由观察器直接用 owner cookie 创建普通修复 Session，改为投递受限的持久事件。旧逻辑在切换时明确单入口归属，防止旧脚本和新服务同时修同一个故障。

事件身份纳入 repository、workflow run、run attempt 和 head SHA，既去重重复投递，也识别 rerun 和已过时失败；派发前重新核对该失败是否仍需要行动。保存旧 handledRuns 与新事件身份映射，不迁移成“修复已成功”。

第一版交付为固定候选、来源明确的现有检查、独立意见及待用户处理的结果。PR 是独立外部发布动作：用户授权创建前先准备可审查结果；创建时固定仓库、base/head、候选摘要和审批版本。仅在实现可查询回执与恢复协议后开放自动创建 PR，不把“草稿 PR”视为天然无外部副作用。自动合并和生产发布不属于 MVP 默认范围。

原脚本提示会让 Agent 直接工作在本地仓库并在验证后创建远程 checkpoint；这不能替代新责任的分支/路径隔离和审批政策。参考 `scripts/github-ci-auto-repair.mjs:650,752`。
## 处理链与结束语义

真实 CI 事件 → 持久 inbox/wake → 核对责任及失败仍有效 → 生成受限决定 → Factory 工作流准入 → 现有 Scheduler/Collaboration → 候选与检查 → 审查/审批 → 结果回执与汇报。

一次修复完成只结束本轮工作，持续维护责任仍保持 active。等待用户时记录审批对象、版本、原因和恢复条件；未经批准不能创建外部发布效果。没有变化或已有同一故障工作进行中时，不重复调用模型或新建执行。

## 退出条件

- 一次责任授权后，真实 CI 事件能推进到固定候选、可信检查和审查结果。
- 所有需要用户批准的动作都停在相应 Gate，审批与具体内容版本绑定。
- 重复事件、重启和回执延迟不产生重复业务工作；未知效果等待核实。
- 每次动作可追溯到责任、事件、政策、命令、执行与证据，预算行为可解释。
- 旧脚本与新服务只有一个负责派发，切换和回退不重复处理故障。

按[共用验证与发布规则](verification-and-rollout.zh.md)交付实际证据。自动 PR 创建仅在具备明确授权和可查询回执时开放；自动合并、生产发布和其他连接器生态不属于本阶段默认范围。

## 当前实现记录（待验收）

CI 观察器现在要求配置 responsibilityId；旧脚本不会继续直接创建修复 Session。已有配置不自动改写，缺少该字段时监视器报错，历史 handledRuns 保留用于首次尝试的迁移去重。服务端重新通过 GitHub API 核实失败和最新运行，事件身份包含仓库、run、attempt 和 head SHA；接收与 wake 在同一 SQLite 事务中写入。固定政策决定通过 Factory 受限准入，不调用模型或直接运行任务；GitHub、Git 工作树与 SQLite 之间仍有不能用事务消除的时间窗口。

此记录不代表真实 CI、候选、审批、重启恢复或发布通过。缺失身份、预算、仓库事实、有效政策或可信来源时应保持等待或拒绝，不自动创建 PR。

旧静态 token 登录已退役；观察脚本使用现有密码登录，从运行环境读取 `AGENTOC_CI_OWNER_USERNAME` 和 `AGENTOC_CI_OWNER_PASSWORD`，不会把凭据写入配置。现有 runner 配置需显式增加 `responsibilityId`；调度器环境必须能够安全取得对应凭据，未配置时失败。GitHub MVP 只接受固定 `agentoc-reviewed-change@3` 和政策指定的现有检查 action；注册和验收仍需实际检查证据与人工操作。远端 Factory 接收另有 `AGENTOC_REMOTE_FACTORY_ENABLED=1` 开关，默认关闭；已有回执读取和新准入分别受目标授权约束。
