# 阶段 4：Workflow Formula、受控集成与交付体系

状态：方案部分已落地，缺项与验证状态见 [实施状态](implementation-status.zh.md)。日期：2026-11-13。上位：[总方案](00-master-plan.zh.md)。前置：[阶段 2](phase-2-execution.zh.md) 的候选与基本验收、[阶段 3](phase-3-team-control.zh.md) 的指挥入口。后续：[阶段 5](phase-5-rollout.zh.md)。

## 1. 目标与范围

把已经运行可靠的任务闭环整理成可复用工作方法，使一个目标能够形成可审查的集成结果、候选产物和有明确授权的发布结果。

本阶段扩展流程和交付，不重新建立任务引擎。基本验收、受控候选和最小集成在阶段 2 已完成，不能等待本阶段才阻止未审查回写。

## 2. 工作包

### P4-01：模板契约与编译

Workflow Formula 至少包含模板 ID、不可变版本与摘要、输入 schema、岗位/能力要求、任务生成规则、依赖里程碑、验收、重试/预算限制和权限要求。

编译过程只产生普通 Goal / Work Contract / Dependency 提案及所需资源说明，不启动进程。编译后走同一个 Factory Control 授权入口，按调用者真实权限裁剪或拒绝。

模板不内嵌可直接执行的任意脚本；检查与构建引用已有受控动作/项目命令。模板输入必须验证路径、项目、目标分支和候选范围，不能把模板参数当 shell 字符串直接执行。

每个实例固定 templateVersion、inputDigest 与生成图映射。模板更新只影响新实例，运行实例通过普通改约命令升级。循环返工必须有次数和预算上限，不能通过模板递归绕过治理。

### P4-02：一套真实流程优先

先从用户实际研发项目中选一套已有可验收流程整理为软件开发模板，不先提供未经业务运行的“万能工厂包”。

推荐的结构是需求/设计决定、隔离实现、固定候选、独立审查、已有可信检查、受控集成与必要的集成后验证。设计审批是否必需由任务授权与用户约定决定，不为所有小修改强制新审批。

Bug 修复模板复用已有缺陷资料和可靠回归；无法复现或没有正确 oracle 时写明不确定性，不能自行创造预期输出。安全模板的扫描或测试能力同样遵守已有授权和真实工具范围。

Factory Pack 初版只是岗位配置与已版本化模板的组合；暂不做远程市场、自动下载和任意执行插件。

### P4-03：审查与验收证据模型

复用 ResultPacket / phase-gates，扩展 acceptance criterion、candidate digest、验证 Run/工具、source commit、实际退出码/结果位置、审查身份和可信采集时间。

每个 Gate 的结果分别是：未运行、进行中、通过、失败、证据不完整、已过期。证据引用指向可读取对象不代表证据可信；需要验证生产者、内容摘要、执行关联及授权。Agent 结论单独作为 review opinion。

实现候选 → 审查/验证 → 接受之间固定同一内容。审查本身不能修改候选；构建/测试在派生工作区运行，生成的文件不混入实现产物。只有实际影响到证据有效性的变化才重做相关检查，避免无意义重复。

### P4-04：多候选集成与 PR/Commit

在阶段 2 单候选集成之上增加顺序队列和依赖：记录 base head、输入候选集合、合并结果 commit、审查与验证的适用对象。

- 集成以当前目标版本 CAS/受控锁为准；发生冲突进入 blocked，由有权限的任务处理。
- 多候选叠加后，原来只验证单分支的证据不能自动覆盖最终组合；仅运行已有且相关的集成检查。
- 审查人与执行者分离，集成 actor 的写权限限于目标仓库/分支。
- 创建 PR、更新 PR、合并和发布是不同外部动作，分别记录幂等身份、输入摘要及实际结果。
- 外部服务响应未知时先查询，不能因“网络错误”重复开 PR、推送或发布。
- 目标 head 变化、候选内容变化或授权撤销会失效对应集成许可。

不得自动覆盖用户未提交工作、强推受保护分支或删除并行 worktree。现有合并/写入策略继续适用。

### P4-05：候选产物和发布 Gate

候选产物记录：源 commit、构建环境/工具链身份、实际构建记录、产物列表与 digest、目标平台、验证范围、已知限制、签名信息引用、审批请求。不得把凭据或签名私钥放入 ResultPacket。

发布授权精确绑定候选包、目标环境/渠道、操作范围和期限。用户已有有效授权可复用；超出授权或任务明确设置最终人工 Gate 时才等待。更换包、目标或关键验证结果后原审批不可继续使用。

发布结果通过现有服务或渠道查询，保留实际版本/产物标识和时间。回滚也是独立授权操作：有明确旧版本和数据兼容前提，不假设撤回代码即可恢复数据库或外部服务。

### P4-06：交付页和长期证据保存

Web/Android 显示目标验收、任务与候选链、集成 commit、真实检查结论、未验证项、待批动作和产物链接。以实际内容为中心，不以 Manager 总结代替证据。

数据库保存紧凑索引和摘要，日志/包放产物存储；活跃执行、未决审批、被验收引用的成果不得清理。保留规则区分短期 staging、长期证据和用户数据。清理前先保存必要源身份、摘要和结果，禁止用一个递归删除误伤项目根目录。

## 3. 模块边界

- 模板编译器只产 Work Graph 提案，执行仍由 scheduler/adapter 完成。
- 集成 operation 和发布 command 复用现有操作日志/审批/外部工具接口；不把外部发布塞进一般自由文本 Run。
- 复用 `result-packets.mjs`、`phase-gates.mjs`、`project-handoffs.mjs`、文件产物和现有构建/发布脚本；是否需要扩展由实际项目决定。
- 相同业务验收写 Work Graph；组织 phase 状态是兼容映射，不能形成第二个验收权威。

## 4. 验证政策与证据

实施前盘点所选真实项目已有的构建、审查、测试和发布流程。现有 `test-phase-gates.mjs`、`test-result-packets.mjs`、`test-result-packets-v2.mjs`、`test-managed-writer.mjs`、`test-orchestration-approval-bridge.mjs` 可支持其协议范围，不能证明安装包、PR 或发布已真实成功。

文档中的流程不授权新增测试；需要新的测试代码、数据集或基础设施时单独申请。对于本来不需要运行测试的低风险任务，允许契约明确采用代码审阅与人工验收，不为了统一模板强迫创造测试。

不能为“走通发布”而实际发布未经授权的包；发布 Gate 可以停在候选已备妥、等待用户的真实状态，此时不能宣称全流程已发布完成。

## 5. 退出条件

- 至少一套来源于真实工作、具有固定版本的模板编译为普通任务图并可追溯。
- 模板不扩权、不静默升级运行实例、不绕过预算。
- 实现、审查、验证、集成和包的内容身份可关联，证据失效规则生效。
- 返工有界且 lineage 完整，不把旧 passed 复制给新候选。
- 候选产物可交付与可检查；发布是否发生、是否授权、是否成功分别记录。
- UI 如实显示 pending / failed / unknown / not_run，缺证据不显示绿色完成。

## 6. 回退

禁用新模板实例化和新发布准入，已有 Work Graph 继续按固化契约处理；必要时等待人工。模板回退不删除旧版本或改写已生成任务。

已发生的 Git 合并/外部发布不能通过回退应用版本撤销；只运行明确授权的补偿操作。保留候选、审批与结果记录，进入阶段 5 的迁移验收。
