# 附件上传性能：实测与后续方案

2026-11-12，三星真机上传 34,603,008 字节文件，经中央 Accounts 中继至电脑，文件 SHA-256 均一致。Windows 测得 18.62 秒，Linux pinggu 测得 28.89 秒，Mac 正式应用测得 24.68 秒；第二次 Mac 分阶段诊断中，手机计算 SHA-256 用时 148 毫秒，协议检查约 1.22 秒、创建上传意图约 0.80 秒，传输阶段标记结束后到确认约 1.70 秒。阶段标记内仍可能包含建链及其他协议工作，不能等同于纯网络字节传输。Mac 与手机时钟未做精密同步，跨设备时间差只能作粗略参考。

这些样本满足当时的 30 秒目标，但不能保证所有正常网络均满足 60 秒，更未达到非传输部分不超过 5% 的目标。要达成后者，必须从用户点击发送到本机文件验证完成建立同一时间基准的分段埋点，分别统计文件读取、哈希、协商、额度预留、建链、首末字节、落盘、校验、额度确认、回执及失败重试。只记录耗时、字节、路径类型和匿名请求关联标识，不记录内容、密钥或账号凭据。

下一步优化方案：

1. 已实现合并准备请求原型，将能力协商与幂等上传意图合并，利用同一个稳定意图完成重试恢复，减少手机与电脑之间的串行往返。电脑应在完成身份、会话权限、大小、幂等键和账号额度校验后返回；旧版电脑回退现有协议。已有单元测试覆盖新旧版本、丢失响应和重复请求。三星至 Mac 正式应用的一次实测中，点击发送至目标端就绪约 14.34 秒（跨设备时钟未精密同步）；手机端记录检查 0.84 秒、标记为传输 11.31 秒、验证确认 1.11 秒，计算摘要 0.158 秒。目标端 SHA-256 与原文件一致。传输标记仍包含建链等工作，且旧版电脑首次尝试新接口会多一个 404 往返，均须继续优化和验证。单次结果不能证明达到 5%，也不能替代 Windows、Linux 和多次测量。
2. 在文件流入时增量计算摘要并在受控的私有暂存区验证，避免同一份文件不必要的重复读取。若复用接收时的摘要，必须证明暂存文件在验证与发布之间不可被替换、修改或跨会话引用；否则继续在发布时重新校验。
3. 研究将额度确认与必要的本地发布操作重叠或引入持久化对账。未证明预留额度在异常退出和过期后仍受约束前，不能仅把额度确认放到后台；现有预留会过期，完成操作也可能因额度变化而失败。断电、网络失败、重复回执、失败补偿和重启恢复均应有确定结果。
4. 对传输建立细分计时，复用安全连接，量化中继建立、首字节、背压、加密、网络和写盘。进度显示按实际字节和阶段更新，避免长时间不动或将确认阶段伪装为传输。
5. 分别在三星到 Windows、Linux 和 Mac 的真实链路重复测量，覆盖新旧版本、冷启动、重试与并发；对至少多次样本报告中位数、尾延迟和失败率。以实际条件下的端到端及非传输耗时验收，不以代码路径或单次最好结果替代。
6. 验收同一条消息选择并发送多个附件：检查每个文件名、大小和内容摘要，记录总耗时与逐文件阶段；覆盖同名文件、混合大小、单文件及整条消息额度边界，并验证中途失败或重试时已完成附件不会重复或丢失。三星至现有 Windows 实例的一次基线中，系统选择器一次选择 4 MiB 和 6 MiB 两个文件，同一条消息发送成功，两个目标文件摘要均匹配，点击发送到第二个文件就绪约 11.17 秒。该基线版本按顺序上传附件；多文件的性能仍需测量，不能用此单次结果代替完整验收。

测试数据仅清理本任务创建且通过 ID、会话和哈希验证的对象。生产文件、用户会话及并行任务不得作为清理对象。

上述多附件基线使用串行版本。源码现已实现单消息最多两个附件并发，并序列化保存各自的完成回执；并发版本的真机性能和失败恢复仍待验证。

附件选择器的所属电脑、会话或新会话项目，以及附件草稿，现使用可恢复的界面状态保存。已用 Compose 状态恢复测试验证两个附件的草稿恢复；选择器打开期间的真机重建和文件读取权限仍须验收。

针对旧版电脑，源码现对明确的合并接口 404 按电脑短暂缓存五分钟，减少后续附件的重复探测；首次探测仍需要一个往返，网络错误不会写入该缓存，升级后到期重新探测。该优化尚未在三星真机测量。

Windows 的现有 AgentoC-ControlPlane 服务曾原位更新合并接口并恢复 ready，旧路由已按哈希备份；随后检测到另一项安装工作重装了该服务，当前路由已恢复为旧版本，部署必须在安装工作结束后重新核对。Linux 候选已针对该实例现有代码准备并通过语法检查；安装和真实端到端验证仍未完成。

重装后的 Windows 实例一度报告 `degraded`、`ownerActivation: OSV_STOPPED`；随后检测到实例进程变化，最新只读健康检查已恢复 `ready`、所有者激活为 `listening`。当前仍是旧路由，不能据此认定新接口部署或上传验收通过。

源码增加默认关闭的阶段计时：电脑端以 `AGENTOC_ATTACHMENT_TIMING=1` 记录中继建立、接收、等待、本地完成和额度确认；手机端仅在 `AgentoC.Upload` 的 DEBUG 日志开启时记录摘要、阶段及请求体写完时刻。日志仅包含随机或进程内匿名关联值、字节数和单调时钟耗时，不含文件名、路径、账号或内容。等待阶段与接收阶段可能重叠，不能相加；手机请求体写完也不等于目标端已验证。手机计时从该文件开始处理时起算，点击发送之前后的会话创建仍须另行计量。电脑端非账号绑定的本地 33 MiB 集成样本本地完成约 55 毫秒；不能把它当作跨网络或已绑定账号的验收结果。

为安全地并行准备中继，源码已增加写入令牌限定的中继取消接口，Android 在失败时尽力并行取消电脑端任务和中央预留，旧服务器的 404 可兼容；如果取消请求也失败，预留仍依赖服务端超时释放。接口尚未部署，已安装版本的准备阶段仍是串行的。

并行预留的 v2 原型现已接入源码：客户端在电脑准备时预留中继，使用随机身份与令牌；中央服务用短期取消栅栏处理乱序和丢失响应，以进程纪元拒绝重启前的迟到请求，并对栅栏容量饱和采取拒绝新 v2 预留的保护。客户端退出或取消请求本身失败时，无人接管的预留仍会在截止时间释放。旧服务或时钟不匹配时回退既有路径。该原型尚未部署或完成三星到 Windows、Linux 的端到端及性能验收，不能认定已达到 5%。

2026-11-12 整合快照验证：从当时完整的 Android 与 shared 已跟踪及未忽略工作区文件构建调试包，复用现有 Google 服务配置。上传客户端、并发批处理、进度、计时、能力回退、选择器所有权和状态恢复的 29 项定向单元测试通过；中央中继真实 HTTP 测试 12 项通过。构建后与当前源码比较，除构建产生的 .gradle 缓存文件外未发现差异；共享仓库仍在变化，部署前须重新比较。此结果不代表并发多附件的真机吞吐或端到端成功，仍需在安全协调现有手机及服务之后实测。

2026-11-12 三星真机对现有实例的并发多附件实测：在同一条消息中一次选择 4 MiB、6 MiB 和 33 MiB，Android 整合调试包最多同时处理两项；Windows 和 Linux 两端均按 a、b、c 顺序显示，六个接收文件的 SHA-256 均与源文件一致。Windows 点击到 33 MiB 手机端确认约 67.4 秒，首批两个文件的 checking 加 preparing 到 transferring 约 21.8 秒；33 MiB 文件开始处理到手机确认约 25.0 秒。Linux 点击到手机端最后确认约 26.5 秒，33 MiB 从开始处理到确认约 12.8 秒。手机与电脑的墙钟未做精密同步，整批点击至手机确认以不同机器时钟计算，仅作近似值；单文件阶段用手机单调时钟。两端会话及各三个目标文件已按会话 ID、文件 ID 和摘要核验后删除，手机和本地测试载荷已删除。测试时中央及电脑端仍为旧版，不能当作完整优化部署或 5% 开销验收；失败恢复、冷启动重复样本和新版服务的实际表现仍需验证。

Windows 当前安装路由校验为 21131f1f…，已针对这一安装构建包含合并上传接口和阶段计时的候选，同时保留当前的账号额度策略；额外验证了无限额度在合并响应中的传播，定向测试 5 项通过。候选及可回滚部署脚本仅完成预检，尚未应用。中央 Accounts 的当前版本已切换，新的 v2 部署脚本重新按当前 release 与文件摘要预检通过；旧服务不提供传输排空接口，重启前仍须确保没有正在进行的中继，且不得覆盖并行更新。

Linux 候选现已针对实例当前 d6b946c… 路由和现有中继任务模块加入合并接口及可选计时，保留其旧版分块兼容行为；候选在 Linux 上通过语法与哈希校验。带回滚的部署脚本预检发现 PID 504737 的另一安装工作仍存活，因而拒绝重启该实例。Windows 的三文件候选也已准备好，预检通过并保留现有账户额度模块；两个候选都尚未应用。

随后对 Windows 现有服务执行了原位更新：部署前检查安装客户端、活动会话、近期待上传文件及服务健康，部署后服务恢复 ready；三个文件摘要均匹配候选，备份位于任务目录。该实例仍可能被并行安装覆盖，最终验收前必须重新校验。中央 v2 及 Linux 候选仍未应用，完整新版链路与性能要求尚未验收。
Linux 候选路由还通过了加载候选代码的合并接口和额度失败重试测试（依赖取自当前源码，因此不是完整旧版 Linux 环境的端到端测试）；需要部署后实测。

Windows 优化阶段的一次三星真机实测：33 MiB，点击发送到手机确认约 17.0 秒（两台设备墙钟未精密同步）；手机单调时钟显示从文件开始处理到确认 14.979 秒，SHA-256 计算 69 毫秒，到传输阶段 1.844 秒，请求体写完 13.875 秒，确认 14.979 秒。目标端文件摘要与源文件相同，会话与两端测试文件已按身份和摘要清理。传输阶段仍包含中继建立，请勿将其全部算作纯网络传输；非传输开销并未证明低于 5%。之后观察到另一安装动作重新部署 Windows：路由回到 21131f1f… 旧版，服务 PID 更新，优化路由不再生效。中央 Accounts 也更新为另一个 release，部署前必须重新做版本和差异校验。

2026-11-12 新版中央中继与 Windows/Linux 路由部署后，三星实机三附件（4+6+33 MiB）验证：Windows 整批从点击到最后确认约 18.2 秒，Linux 约 25.6 秒，顺序正确、六份目标文件摘要全部匹配。中央服务随后被其他部署替换；已将新版中继与当前服务的 workspace-authority 改动合并，12 项中继测试通过并重新部署。Mac 正式应用三附件在替换前的旧中央版本下约 21.5 秒、三个摘要匹配；中央重新部署后，Mac 又以 33 MiB 单文件实测约 20.6 秒、摘要匹配。整批墙钟跨设备、未经精密同步，仅作近似；手机单文件阶段使用单调时钟。所有测试会话和载荷均按身份、摘要清理。

Linux 随后使用临时计时单次测量 33 MiB：手机从文件处理到确认 16.466 秒；电脑端中继打开 1.558 秒、接收 12.599 秒、本地完成 30.15 毫秒、额度绑定 0.36 毫秒、额度确认 438.52 毫秒。接收与等待阶段重叠，不能求和，且手机传输阶段包含中继建链。临时服务配置已移除并恢复服务。该样本不满足或证明不了非传输时间低于 5%。

收尾补充：客户端在合并意图成功并完成所有者、会话和额度校验后，可并行启动加密写入与电脑端中继任务；旧目标和受限作用域继续走原有顺序路径。定向测试覆盖写入提前开始、启动失败时取消写入与预留。该最后优化的实际链路表现仍需实机验证，以上三系统和多附件结果来自前一整合版本；不能将请求体开始写入或写完等同于网络首末字节，亦不能据此认定 5% 目标达成。Mac 测试包为临时签名，尚未经过 Apple 公证；三系统最小全新环境安装验收仍未完成。
