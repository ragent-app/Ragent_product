# Android 本机实例账号联动与远程连接补齐方案

状态：方案草案，供评审；本文提出的联动协议、接口和后台能力尚未实现。适用范围是现有常规 Android APK 的可选本机实例，以及 Termux 中 Ubuntu 24.04 ARM64 的 Ragent 服务；不是新 APK 类型，也不要求公网 IP、端口映射、root 或桌面环境。

## 1. 现状与目标

本机预览已提供配对文件：`lib/proot-local-pairing.mjs` 导出版本、实例 ID、回环地址和本机 bearer；服务只接受直接回环请求，Android 有本机实例独立目录与导入入口。它证明手机持有本机控制凭据，并不证明手机账号、实例归属或远程访问权限。现有实机已在三星手机验证本机连接；不同设备和完整远程任务尚不能据此推断可用。

现有账号体系中，实例身份、Accounts 绑定、Android 账号设备凭据及可信设备授权已有独立实现。`chat/account-pairing-service.mjs` 提供已绑定实例发起的短期一次性账号交接；`chat/router-device-pairing-routes.mjs` 和 `lib/owner-account-auth.mjs` 有 account-intent、实例归属及管理流程。现有短期交接只能完成一次授权，**不提供本机两端持续登录态同步**，也不能宣称已支持本机无扫码的双向入口。

当前 PRoot 模式主动限制为回环本机：`lib/config.mjs` 限制监听地址，`chat-server.mjs` 对账号恢复、目录发布、配对轮询、权限监控和账号设备 P2P 恢复有 PRoot 分支限制；`lib/auth.mjs` 的 PRoot 分支不接受普通可信设备 bearer，`chat/ws.mjs` 拒绝相关信令入口。便携包当前也没有随包提供普通 Linux 发布包中的 P2P host。包装入口还清除继承的账号和 TURN 等环境变量。因此其他平台已有的发现和连接代码，不意味着 PRoot 已支持被其他设备远程访问。

本方案补齐：首次经用户明确同意后，本机 APK 与实例持续联动账号登录、切换和退出；凭据各自独立；实例可经现有账号发现、可信设备授权与标准直连/中继链路供其他授权设备访问；离线本机控制保留。旧服务、未安装 Termux 的手机和既有远程电脑连接保持兼容。

## 2. 三类身份和凭据

| 类别 | 持有者与用途 | 不可替代的边界 |
| --- | --- | --- |
| 手机账号会话及账号设备凭据 | Android 自己登录 Accounts、管理目录和发起授权；由账号服务签发并存入 Android 受保护存储 | 不复制账号 access/refresh token 给实例，不把账号登录视为实例控制权 |
| 实例身份与账号归属 | Ubuntu 实例持有实例私钥和持久 `instanceId`；Accounts 记录归属与授权关系，实例使用自己的签名证明和服务端认可的授权 | 不把实例私钥、实例凭据复制给手机；账号归属不由本机 bearer 单独决定 |
| 本机配对凭据 | APK 持有导入的实例本机 bearer，用于经严格回环直连控制本机实例 | 不是账号会话、云端归属证明或远程通行证；登出账号不自动删除它 |

远程设备另有其各自可信设备凭据；它不是手机账号令牌或本机配对文件。上表是三个安全领域，不能用同一个字符串或文件充当彼此的凭据。

## 3. 首次授权与持续联动

推荐默认：首次建立同机账号联动必须由用户在清楚看到手机账号、实例身份与授权范围后明确同意；随后只在该实例、该账号和该关联有效时，自动续期同账号授权与同步状态。一次确认不授权更换为另一个账号、合并账号、接管已有归属或传播明文凭据。

首次双向路径：

1. **手机已登录、实例未绑定**：经已认证的本机通道发起显式绑定意向，复用现有实例签名和 Accounts owner account-intent/claim 授权链，由 Accounts 验证并分别颁发实例所需授权；不得把 Android 的账号 token 交给实例。现有未绑定实例需要一次性 claim challenge，是否能安全地经本机已认证通道传递并被现有路由接受，必须由实现阶段验证；不足时增加受限的一次性事务，不绕过 claim。
2. **实例已绑定、手机未登录**：用户在手机明确选择使用该实例的账号；复用实例发起、短期有效且一次性消费的 account-pairing v4 和设备证明，由 Accounts 给 Android 签发它自己的账号设备凭据。同机通道承载邀请信息，避免自己扫描自己的二维码；邀请过期、撤销和重放均失败。现有二维码流程并非现成本机自动登录接口，需补受限入口及 UI。
3. **两端同账号**：核验账号权威标识与实例身份后幂等建立关联；仅刷新本端凭据，不替换其他端的凭据。
4. **两端不同账号或实例已有其他 owner**：进入冲突状态，显示脱敏身份和影响；绝不静默覆盖、合并或迁移。用户先明确选择退出关联账号或经过确认解绑，再启动新授权；服务器原有 owner 冲突判定仍是权威。

持续联动同步的是经认证、带版本的**状态事件和授权事务**，不是复制登录 cookie、账号 token 或把一次性 handoff 当长期同步。一个本机关联只对应一个 Android 安装身份和一个实例身份；关联密钥/设备证明、来源、目标、账号权威 ID、generation、事件 ID、时间和有效期都必须绑定。接收方校验同机认证与授权关系后，再独立向 Accounts 完成本端会话的建立或续期。自动续期只允许既有已同意的同账号、同关联、未撤销且 generation 未被退出栅栏取代的状态；切换到其他账号需要用户明确发起并重新授权。

### 状态机与失败处理

| 状态 | 可见行为和转换 |
| --- | --- |
| 未关联 / 本机不可达 | 仍可使用已有本机目录；提供授权入口，服务不可达时提示打开 Termux |
| 待用户同意 | 展示双方账号、实例和权限；取消即回到原状态，不更改任何归属 |
| 授权中 | 绑定身份与一次性事务；允许幂等重试，网络失败显示待重试，不报告成功 |
| 已关联同账号 | 双端各持独立会话；在有效授权内续期，并同步登录/退出事件 |
| 账号冲突 | 暂停自动同步，不覆盖任一端；只能显式解决后重新发起 |
| 退出待同步 | 发起端先落盘退出栅栏并退出本端；对端未确认时显示待同步且不允许旧状态恢复 |
| 已退出 / 已撤销 | 不自动用对端残留会话重新登录；只有用户明确的新登录可开启新的 generation |
| 离线 / 状态待确认 | 保留本机回环访问；账号或云端撤销待联机确认，不能显示为已完成 |

同步处理按关联序列化，事件持久化后再确认；重复、乱序、重放的旧 generation 不生效。建议由 Accounts 或专门的联动协调器按关联维护权威递增 generation，以期望前代的原子比较更新和事件 ID 做幂等，双方分别持久化最高代次、退出 tombstone 与待发送队列。该同步状态不能放在会随账号退出清空的 profile 内；本机受认证通道只提交绑定双方身份的意图，不能替代账号服务的授权。重启恢复时先加载退出 tombstone 和待同步队列，再允许续期或重放事件。并发离线切换和退出不存在可证明的实时全序：冲突或无法确认时退出优先，暂停同步并要求用户明确处理。冲突、凭据被撤、目录损坏和关联身份变化时默认停止自动授权并要求用户处理。

## 4. 退出、解绑与撤销的产品语义

推荐将“退出当前同机账号”定义为**同时退出这台手机 APK 和与其已联动的本机实例的账号会话**。用户发起后，本端先持久写入递增的退出 generation/tombstone，清除本端账号会话并向对端投递退出；对端确认后两端均显示已退出。两端各自的账号会话及本联动所用设备凭据应分别失效或撤销，云端撤销未确认时显示待同步；不得调用账号全设备注销。此操作保留本机 bearer、实例 ID、实例用户数据和离线本机控制，不注销该账号在其他手机或电脑上的会话。

离线或对端被冻结时，本端立即退出并显示“另一端待同步”；对端重新可达后必须先处理持久退出事件，只有确认后两端才显示同步完成。若另一个端在断联期间恢复旧会话，其旧 generation 不能覆盖 tombstone，也不得自动为已退出端重新登录。两端长期离线时无法承诺远端已经退出；用户可重试或在账号设备管理中单独撤销。新的登录必须由用户明确发起，不能由后台旧会话触发。

退出会话与**解绑实例归属**分开：退出默认不改变 Accounts 中实例 owner 归属，也不主动撤销其他远程客户端的设备授权；实例退出账号后不再对外维持账号在线发布/远程连接，已建立的远程会话按权限边界主动断开。保留的云端归属/其他设备授权是持久授权记录，不代表实例在线或可访问；用户重新明确登录同一 owner 后，仍须经有效授权恢复。若产品要求退出时同时撤销现有远程设备，应作为单独、明确说明影响的操作，而不是悄悄扩大退出范围。

“解绑实例账号”需要独立确认，通过现有 owner 授权管理流程撤销实例与账号的云端归属及其相应远程授权、停止发布/恢复，清除本机相关账号会话与关联；本机配对与数据默认保留。服务端必须确认成功才显示云端解绑完成；离线时记录待处理并明确提示云端仍可能保留归属，不将本地删除伪装成远程撤销。“撤销某台设备”只影响选定设备和它的连接；“删除本机配对”才删除本机 bearer 的 Android 副本或触发实例端轮换，三者均不是相同操作。远程撤销、实例重置或 token 轮换后按服务端权威结果收敛，失效凭据不能自动恢复。

## 5. 无公网地址的标准远程连接

复用既有账号目录和实例身份：实例经 Accounts 授权发布最小发现信息，其他已授权客户端按账号发现实例并完成可信设备身份验证；沿用现有 rendezvous、信令与 TURN 中继策略。当前 bootstrap 为 `relayOnly=true`，本轮不将直连作为既有能力或必选交付；如未来加入直连，须另行验证网络与策略。实例对公网无需暴露固定 IP 或入站端口，本机 bearer 从不作为远程凭据。实现需梳理实例注册/在线心跳、可信设备授权与撤销、P2P host 生命周期、信令与 TURN 凭据发放，并在 PRoot 显式启用与其安全模型相适配的功能；不能仅取消 `isProotRuntime` 守卫就宣称支持。

现有架构和代码提供复用基础，PRoot 包缺少可运行、已验收的 Linux ARM64 P2P host 和专属启动/恢复集成。现有 `lib/p2p-host-agent.mjs` 使用受策略检查的本地代理转发至 loopback；必须同时设计独立、受密码学验证的远程设备 principal/入口，复用或扩展可信设备凭据及撤销检查。不能相信普通 localhost 来源或伪造的代理 header，更不能将本机 owner bearer 传给远程载体或信令。账号网络中断、授权无法确认或撤销时远程入口 fail-closed，本机 token 独立可用。须构建并验证 ARM64 sidecar、配套许可证与失败回收。中继不可用、实例离线或账号已撤销时给出可解释状态；中继需网络和相应服务容量，不能保证任意网络必定可达。离线时本机 APK 与本机实例仍走原有回环身份验证，不依赖 Accounts、信令或 TURN。

## 6. Android 后台约束

在已验证的三星手机上，Termux 转入后台后 PRoot/Node 曾被冻结；仅将 Termux 电池设置为“不受限制”仍发生冻结。分屏保持 Termux 可见时服务恢复响应；wake lock 的效果尚未验证。首版指导用户在 Termux 的交互 Ubuntu 会话中运行服务并保持可见，不承诺后台常驻或系统重启后自动启动；远程目录需如实显示离线或不可达，不能把后台保活当成已解决。

首选继续评估现有 Termux 自身的前台服务、用户主动启用的 wake lock、前台可见性提示与单应用电池策略引导，逐设备验证其有效性和耗电影响；不能假设 Android APK 自己的前台服务能保活另一个 Termux 应用，也不默认修改全局系统策略、要求新插件、root 或跨应用隐式权限。若不能稳定后台运行，降级为保持 Termux 可见、实例不可用时显示离线，远程用户可明确重试。后台稳定性是远程能力发布门槛，可与账号联动并行调查，不阻塞离线本机和账号联动方案。退出同步遇到冻结时按“待同步”处理，不能等待假成功。

## 7. 拟改动边界与接口

以下是实施落点和候选职责，**不是声称现有 API 已具备这些能力**。先通过版本化 capability 协商，再启用新路径；旧版本保留现有本机和远程行为。

| 层 | 现有文件 / 模块 | 拟增或调整 |
| --- | --- | --- |
| Android 入口与状态 | `android/app/src/main/java/com/andysagent/agentoc/MainActivity.kt`、`TargetRuntime.kt`、`android/core/datastore/.../ClientConfigStore.kt` | 本机关联、冲突、退出待同步和远程状态；本机目录继续独立，不更改 APK 身份 |
| Android 账号与安全存储 | `android/core/auth/.../AccountSessionManager.kt`、`PairingAuthenticator.kt`、`CredentialStore.kt`、`AccountProfileTransitions.kt`，`android/app/.../AgentoCApplication.kt` | 接入账号建立/切换/失效/退出及目录切换；明确同意、双向一次性授权、独立关联状态、退出 generation/tombstone 和持久待投递，状态不能随账号 profile 清除 |
| 本机实例认证 | `lib/proot-local-pairing.mjs`、`lib/auth.mjs`、`chat/ws.mjs` | 延续仅回环 bearer；增加严格限定的能力协商与账号联动事务入口，不让普通本地 bearer 升级为云端授权 |
| 实例账号与事务 | `lib/owner-account-auth.mjs`、`chat/router-device-pairing-routes.mjs`、`chat/router-account-pairing-routes.mjs`、`chat/account-pairing-service.mjs` | 复用已有 claim / v4 事务；仅在需要时新增受认证、短期、单次、实例和 Android 设备绑定的本机交接及持续状态事件接口 |
| Accounts 服务 | `accounts/` 下 owner-auth、account-pairing、实例目录与撤销相关路由/存储 | 明确 owner 归属、签发各端独立凭据、权威撤销和 revision；如现有协议不够，先定版本化 schema 与迁移，不能假设已有同步 API |
| 远程与生命周期 | `chat-server.mjs`、`lib/config.mjs`、`lib/p2p-host-agent.mjs`、`p2p/`、现有信令/TURN 组件、`packaging/proot/` | PRoot 专属可控发布、独立远程 principal 验签及撤销检查、ARM64 sidecar 打包与启动/停止/恢复；不改变普通 Linux 包默认行为 |
| 文档 | `docs/android-proot.md`、本文及相关账号/远程说明 | 按实际交付更新权限、离线、后台和故障恢复；保留前后版本兼容指引 |

具体新接口名和 JSON 字段应在协议评审中定稿。至少需要：读取本机联动能力与双方脱敏账号状态；创建/确认/取消绑定事务；投递并幂等确认版本化登录/退出事件；读取待同步与撤销状态。所有写操作须绑定当前实例身份、Android 设备证明、关联及 generation，并受现有账号服务权限检查；敏感字段不得出现在 URL、日志或共享文件中。

## 8. 实施顺序与交付判据

1. **协议和撤销语义**：冻结凭据边界、账号身份比较、同机授权、generation/tombstone、失败与迁移契约；确认现有 account-intent/v4 是否可安全复用。先完成威胁建模和服务端权威边界评审。
2. **同机双向绑定**：实现两个首次方向、能力探测、明确同意和冲突处理；不接入远程发布。依赖阶段 1 的签名、一次性事务和存储契约。
3. **持续状态同步**：实现退出先落盘、幂等事件、离线待同步、重启恢复、显式重新登录与同账号续期；先验证不复活旧会话，再启用默认联动。
4. **可选标准远程链路**：为 PRoot 实例适配目录注册、独立远程 principal、可信设备、ARM64 sidecar 和现有 TURN 中继策略，验证撤销、离线和进程生命周期；不依赖公网入站。依赖阶段 1–3 的真实账号归属与设备授权，以及已验证的后台运行宿主。
5. **体验和发布**：完成后台状态提示、兼容旧服务、安装文档和发布材料；后台保活单独作为能力验收，不以本机连接成功代替。常规 Android APK 和 PRoot 包均须对应实际代码版本。

工作规模按交付项评估：同机联动涉及 Android、实例和 Accounts 三端协议与状态存储，是主要工作；远程入口和 ARM64 sidecar 是独立增量，涉及设备身份验证和网络服务；后台宿主是并行的不确定性最高项，需目标设备调查。验收需真实账号、至少两个授权客户端及代表性网络，不以未经验证的日历日期承诺交付。

最小真实验收矩阵：手机已登录到未绑定实例、已绑定实例到未登录手机各一次；同账号重复操作幂等；不同账号冲突/取消不覆盖；任一端主动退出同步另一端，断网或冻结时 pending、恢复后收敛且重启/旧事件不复活；显式解绑、单设备撤销与其他客户端不受误伤；网络断开时本机 bearer 仍可访问；另一授权设备经不需公网入站的现有 TURN 中继策略访问，撤销或账号授权无法确认后失败，本机 token 不能远程使用；服务重启/设备离线如实显示；未装 Termux 和旧服务的普通远程连接不回归。另测三星前台/分屏/后台冻结并记录设备、系统、设置与结果。

账号联动交付需满足：两向首次授权和持续状态语义均完成；无 token 复制或静默跨账号覆盖；退出和解绑有可证明的服务端/本地结果；离线及撤销闭环通过真实数据验证。可选远程能力另需代表性网络下的真实中继、撤销与后台稳定性证据；后台尚不稳定时不得宣称远程常驻可用。文档须清楚标记后台限制与不支持项。账号联通、UI 显示或单次 handoff 不能单独作为完整交付证据。

## 9. 风险与评审决策

- **权威与竞态**：Accounts 的 owner 绑定、设备授权和本地退出 tombstone 各自有不同权威；实现必须定义原子持久化、跨端同时退出/切换和故障恢复，避免旧会话复活或错误回滚。
- **现有协议复用**：v4 是短期单次流程，未绑定 claim 与本机认证通道的组合仍需确认；若不满足端到端绑定，新增版本化受限事务，而非降低证明要求。
- **安全与隐私**：本机 bearer 可控制实例，手机账号和实例绑定仍须单独同意；限制共享文件生命周期、日志、凭据访问及状态展示中的账号信息。
- **PRoot 隔离限制**：同 UID 的 PRoot 任务可能读取私有文件，目录权限不构成与这些任务之间的操作系统级隔离。不得把本方案描述成提供了该隔离；凭据隔离和高风险任务保护需单独设计。
- **远程可用性和成本**：PRoot host/网络栈、TURN 配额与三星后台冻结均可能导致不可达；用在线状态和明确错误呈现，不承诺无条件常驻。
- **产品默认决策**：推荐采用第 4 节的两端退出、保留归属和其他设备授权，以及单独确认的解绑/撤销；若要改为退出即解绑或跨设备全局退出，必须作为改变权限与数据访问的明确产品决定和迁移，而非实现细节。
