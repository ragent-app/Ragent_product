# 加密附件中继：当前限制与大文件支持方案

更新日期：2026-11-19

范围：Android 客户端、桌面目标端和中央 Accounts 加密附件中继。

## 结论

当前加密中继按**单个密文传输体不超过 64 MiB**设计，尚不支持把一个大文件拆成多个中继段。超过上限的附件仍可按桌面端上传契约走可续传的分块上传，但速度可能较慢。

本次 Samsung 上传样本为 78,830,947 字节（约 75.2 MiB），超过加密中继限制，因此客户端选择普通分块路径。这个结果不能用来衡量小于 64 MiB 文件的中继速度。

64 MiB 是当前实现和服务容量策略，不是 AES-GCM 加密本身的限制。若要让很大的文件也走加密中继，推荐增加**分段、可续传的加密中继协议**，而不是直接把单请求限制提高到数 GiB。

## 当前行为和限制

| 环节 | 当前限制 | 超限或不可用时的行为 |
| --- | --- | --- |
| Android 中继加密 | 使用 AES-GCM 记录；每条明文记录最多 256 KiB，密文帧每条增加 36 字节。客户端要求明文不超过 64 MiB，且计算后的整份密文也不超过 64 MiB。 | `wireSize()` 不接受该文件；中继条件不成立。 |
| Accounts 单个预约 | 每个中继预约最多 64 MiB 密文；HTTP `PUT` 请求体也限制为 64 MiB。 | 不能把整份更大的文件作为一个中继请求发送。 |
| Accounts 并发容量 | 默认总预约密文最多 256 MiB，全局最多 64 个预约，每账号最多 4 个。普通预约最长 5 分钟；v2 预分配票据最初最多 120 秒，双方接入后活动传输最多再保留 5 分钟。 | 容量不足时拒绝新的预约；活动连接不会无限续期。 |
| Accounts 生命周期 | 不在云端落盘，也不持有解密密钥；写端和读端接入后，以有背压的流直接转发密文。传输中断或超时会中止该次流并释放预约。 | 当前预约不是可在云端恢复的文件缓存。 |
| Accounts 接口频率 | v1 预约端点配置为每分钟 12 次；v2 预约、能力查询、取消和密文读写端点各配置为每分钟 24 次。 | 高频小段会消耗更多请求额度；分段大小和每账号并发需一起设计。 |
| Accounts 接收能力 | `RAGENT_ACCOUNTS_ATTACHMENT_RELAY_ENABLED=1` 才启用；相关预留接口有速率限制。 | 未启用时不会提供中继预约能力。 |
| Windows 目标端能力 | 目标端需在上传契约发布 `encryptedRelay`；目前要求 `RAGENT_ASSET_RELAY_ENABLED` 未设为 `0`，并且 Accounts broker 已配置。路由还要求 owner 或 trusted device 身份、有效会话/资产权限。 | 没有中继能力时，Android 使用普通分块路径。broker 已配置只说明 URL 可用配置，不代表中央 Accounts 中继实际启用或可达。 |
| Windows 接收状态 | 当前中继启动要求该资产的分块 checkpoint offset 为 0。普通分块已经写入后，不能直接把同一个上传切换到中继模式。目标端接收 job 默认最多 16 个、接收超时 180 秒，结果保留 10 分钟。 | 已开始的分块上传继续走原路径；必须避免两种写入模式并发覆盖同一资产。 |
| 客户端与接收超时 | Android 中继 HTTP 客户端连接超时 15 秒，读/写超时各 120 秒；目标端中继接收 job 超时 180 秒。 | 低速大文件可能先撞到读/写或目标端 job 超时，即使尚未达到字节上限。 |
| 普通分块回退 | 上传契约 v2 每次 1 MiB；旧契约 v1 每次 256 KiB。桌面目标默认稳定上传上限为 1 GiB，实际值仍由目标端契约和账号额度决定。 | 可上传大于中继上限的文件，但每个分块需单独确认，实际吞吐会受往返和目标端写入影响。 |

Android 的有效明文上限还要扣除密文开销。按目前 256 KiB 记录、每条增加 36 字节计算，在 64 MiB 密文上限下，单文件明文上限是 **67,099,648 字节（约 63.991 MiB）**，而不是完整 64 MiB。

客户端只有在目标端声明正确的 `encryptedRelay` 版本和记录大小、客户端有 relay transport、文件通过密文大小检查并成功取得预约时，才会调用中继。否则会进入本机分块上传。对于可选中继接口明确返回 404/501 或目标端检测到已有分块 checkpoint 的模式冲突，当前实现会回退；其他预留或传输错误通常会让上传失败，不能理解成所有错误都会自动回退。

## 大文件中继方案

### 设计目标

让单个逻辑附件可以超过 64 MiB，并继续保持：

- Accounts 只转发密文，不落盘、不拿到解密密钥。
- 手机端和目标端都按有界缓冲流式处理，不把整个文件装入内存。
- 中断后从目标端已持久确认的位置恢复，不重复发布、不丢字节。
- 云端只为当前活动分段保留中继容量；不为数 GiB 文件预约等量的云端空间。
- 账号额度、目标磁盘空间、会话权限、取消和过期清理继续有效。

### 推荐协议：一个文件，多段加密中继

1. **建立稳定的文件上传意图。** 目标端先检查账号额度、会话权限、文件大小、剩余磁盘空间和文件 SHA-256，并创建私有暂存文件及可持久化 checkpoint。文件大小上限继续由目标端契约和账号额度给出；分段中继本身不自动把文件上限变成无限。
2. **协商 v2 能力。** 新契约返回最大文件大小、最大密文段大小、记录大小、协议/算法版本、是否支持续传以及目标端 checkpoint 语义。保留现有 v1 单段协议，不改变旧字段含义；旧客户端继续使用现有路径。
3. **按有界段预约和传输。** 初始可评估 4–16 MiB 明文段，并选择 1 MiB 整数倍，确保密文小于现有单次 64 MiB HTTP 上限。第一版每个文件一次只传一个段；段成功提交并更新目标 checkpoint 后，再预约下一段。不要为完整文件创建一个超大 reservation。
4. **端到端加密每一段。** 继续使用经审查的 AES-GCM 记录格式。每段使用唯一的传输身份/密钥域；认证数据绑定文件上传 ID、目标资产 ID、总长度、段编号、段偏移、段长度和记录序号。密钥只通过现有已认证的手机到目标端控制通道发送，不能放入 Accounts 请求。重试不得在相同密钥和 nonce 下加密不同明文；重发已生成的密文，或为新尝试使用新的密钥/nonce 域。
5. **目标端按段安全落盘。** Windows（以及后续启用此功能的其他桌面平台）只在私有暂存目录中解密和写入指定偏移；验证段长度、段摘要、顺序和 checkpoint 后才提交进度。未完成的段不得推进持久 checkpoint。文件全部到齐后，再验证整个文件 SHA-256，并以原子操作发布为可用附件。
6. **恢复和取消。** 恢复时以目标端持久 checkpoint 为唯一权威，从第一个未确认的段申请新的短期中继预约；不能仅凭 Accounts 返回的写入完成响应认定目标端已落盘。取消、权限撤销、目标重启、手机重启、磁盘满、账号额度变化和 reservation 过期都要有确定清理或恢复结果。
7. **按活动和总量控制资源。** 保留短期未开始预约；活动流采用空闲超时、进度续租和每段最长时长，而不是让固定 5 分钟计时误杀慢速但仍在推进的传输。继续限制每账号和全局并发段数、预约字节、速率及失败重试，拒绝超限请求并在完成、取消、超时和进程关闭时释放容量。
8. **支持 Android 源文件恢复。** 文件源必须可重开或可按偏移重新读取。应用恢复后重新核对大小和 SHA-256；若系统 URI 权限已失效或源文件改变，应明确失败并要求重新选择，不能从错误内容继续续传。

### 为什么不直接提高 64 MiB

当前 Accounts 中继是一次性双端流，容量按预约和活动连接统计；它没有持久化对象存储，也不能在服务重启后恢复正在转发的字节。单纯提高 `bodyLimit` 和 `maxTransferBytes` 会让单个慢连接长时间占用预约和接收 job，断线后仍需重传大段，而且固定的 5 分钟预约/目标端接收超时并不适合超大文件。若只提高一个服务的限制，客户端、Windows 目标端、反向代理和中央 Accounts 的上限还会不一致。

因此保留每段的 64 MiB 硬上限，用多段和目标端 checkpoint 支持大文件，更容易保持内存、重试成本和账号资源可控。需要超过当前桌面端 1 GiB 默认上限的场景，还要单独提高并核实目标端、账号额度和磁盘策略。

## 实施阶段

1. **定策略与协议**：产品先确定最大文件大小、最小上传速率、可接受的恢复粒度和每账号并发；固定 v2 manifest、段状态机、授权边界、加密 AAD 和续租语义。
2. **Accounts 分段管道**：增加带版本的段预约、读取/写入、取消和过期处理；保持流式直通、密文上限、速率限制和容量账本；不要接收或记录密钥、文件名、路径和内容。
3. **桌面目标端暂存与恢复**：接入现有 stable upload intent/checkpoint；实现按段接收、解密、私有暂存、段提交、整体摘要校验及原子发布。先让 Windows 能力完整，再按同一契约扩展 macOS/Linux。
4. **Android 分段客户端**：按能力协商传输；流式加密与上传；展示真实字节进度和“正在中继/分块回退”状态；记录匿名关联 ID、段号、字节数、耗时和明确的回退原因，不记录文件名或内容。
5. **逐步启用**：先在非生产目标验证中央、目标端和 Android 三方版本及代理超时一致，再用受控账号开启能力；保留旧客户端回退，并监控完成率、速度分位数、续传率、容量拒绝、超时和残留暂存清理。

## 未来验收标准

- 使用大于 64 MiB 的真实文件，确认日志明确显示 `encrypted-relay-segment` 路径，而不是只看通用的 `transferring` 阶段。
- 手机、目标端和最终文件 SHA-256 一致；完成前附件不可见，完成后只发布一次。
- 在段中断、段确认丢失、手机重启、目标服务重启、Accounts 重启、重复请求和取消后恢复时，不丢失或重复发布数据，且从已确认 checkpoint 继续。
- 覆盖超额、并发饱和、429、404/501、权限撤销、磁盘不足、源 URI 失效及源文件变化；验证释放 reservation 和清理部分暂存文件。
- 以多个大小和网络条件报告端到端时间、中位数、P95、失败率和重传量；确认内存使用有界，并核对账号/全局并发限制确实生效。
- 隐私审查确认 Accounts 日志和 Android/桌面诊断不包含密钥、token、文件名、路径或文件内容。
